## 3. AKS — throughput ceiling (`ramp` 10 → 50 → 100 VUs)

| scenario | reqs | rps | med | p95 | max | failed (excl. 429) | **throttled 429** | real success | verdict |
|---|---|---|---|---|---|---|---|---|---|
| health | 77,859 | 456 | 93.8 ms | 181.7 ms | 60,001 ms | 0.01% | **99.6%** | ~0.4% (~300 reqs) | ❌ |
| citizen-journey | 27 | 0.8 | 5069 ms | 5534 ms | 5844 ms | 0 | 0 | n/a — **aborted** at the p95>3 s guard | ❌ |

- **health ramp**: 100 VUs generate 456 rps, but **99.6% are rejected 429** — only the
  ~100/minute permit gets through. `max=60 s` is the 10 queued requests (`QueueLimit=10`)
  waiting a full fixed window. The pod barely worked (CPU 16 m mid-run): the limiter
  rejects before any application logic runs.
- **citizen-journey ramp**: each Bearer request blocks ~5 s on Redis, so throughput
  collapsed to 0.8 rps and the run self-aborted on the cluster-protective `p95 > 3 s`
  guard — the Redis stall is so severe the path never even reaches the rate limiter.

## 4. Root-cause analysis

### A. Redis 5 s stall on every authenticated (Bearer) request — DOMINANT latency defect
Pod logs during a slow request:
```
Executed DbCommand (2ms) ...                     ← DB is fine
StackExchange.Redis.RedisConnectionException: The message timed out in the backlog ...
  (5000ms) - UnableToConnect on localhost:6379 ... command=HMGET ... timeout: 5000
Request finished GET /api/v1/wallets - 200 ... 5013.6305ms
```
- `appsettings.json` ships `ConnectionStrings:Redis = "localhost:6379,…,syncTimeout=5000"`.
- The Helm value `api.redisConnectionString` is **empty**, so `ConnectionStrings__Redis`
  is **not** injected and the app uses the `appsettings` default. With a non-empty
  connection string the Infrastructure layer takes the **Redis** branch (not the intended
  in-memory fallback), so the distributed token-blacklist lookup (`HMGET`) on **every
  authenticated request** blocks the full `syncTimeout=5000 ms` against a Redis that
  isn’t there, then proceeds.
- Impact: citizen Bearer path p95 ≈ 5.1 s (**10× the SLA**), independent of load.
  API-key and anonymous paths skip the blacklist lookup → 60–140 ms.
- **Fix (config/app, not resources):** set `api.redisConnectionString` to a reachable
  Redis, **or** to a fail-fast string (`syncTimeout=200,connectRetry=0`), **or** force the
  in-memory distributed cache in `Testing`. (A fail-fast string was the intended bounded
  remediation but fell outside the authorized resource-bump scope — see §5.)

### B. Global rate limiter 100/min per remote IP, no forwarded headers — DOMINANT throughput defect
`Program.cs` registers an unconditional `GlobalLimiter` = `FixedWindow{PermitLimit=100,
Window=1min, QueueLimit=10}` partitioned by `context.Connection.RemoteIpAddress`, and
the app does **not** call `UseForwardedHeaders`. Behind the NGINX ingress the remote IP
is the **ingress-controller pod**, so **all clients across the whole deployment share one
100/min bucket**. A 100-concurrent-user SLA is unattainable through it.
(The `appsettings RateLimiting:*` section — Authenticated 100/min, etc. — is **not wired**
to this active GlobalLimiter.)
- **Fix:** add `UseForwardedHeaders` + `ForwardedHeadersOptions`, partition by
  authenticated principal/tenant, and raise the limit to the SLA concurrency.

### C. Single replica / 300 m CPU — NOT the bottleneck (proven in §5).
DB latency on the shared **B1ms** PostgreSQL was a non-factor at this load (`DbCommand`
2–7 ms throughout).

## 5. Remediation delta (authorized resource bump)

Bounded, in-namespace `helm upgrade`: **replicas 1 → 2, CPU limit 300m → 1000m**
(requests 25m → 100m). Worst scenario re-run, before/after:

| metric | before (1×, 300m) | after (2×, 1000m) | delta |
|---|---|---|---|
| citizen-journey `steady` p95 | 5093 ms | 6564 ms | **no improvement** (worse, within noise) — not CPU-bound |
| health `ramp` real throughput | 456 rps wire / ~100 per min served | 5.4 rps served, p99 39.8 s | **no SLA gain** — limiter is global per-IP; extra replica just added queue-blocking |
| peak CPU under load | — | **213 m across 2 pods** (≪ 1000 m) | CPU never the constraint |

**Conclusion:** the resource bump does not move either SLA metric. The ceilings are the
two **config/app defects** (A, B), not compute. The namespace was **reverted** to its
original footprint (replicas=1, cpu 25m/300m; Helm revision 3) after the test.

## 6. SLA verdict per scenario (@ 100 VU, as deployed)

| scenario | app latency (under cap) | @100 VU | blocker |
|---|---|---|---|
| health | ✅ 58 ms | ❌ | global 100/min limiter (B) |
| citizen-journey | ❌ 5.1 s | ❌ | Redis 5 s stall (A) + limiter (B) |
| credential-ops (API-key reads) | ✅ 142 ms | ❌ | limiter (B) |
| presentation-verify (verify op) | ✅ ~61–120 ms | ❌ | limiter (B) |

**Overall: the deployed configuration does NOT meet the SLA.** The application core is
fast (health/credential/verify all < 150 ms p95 under the cap, DB ~2 ms), but two
configuration defects gate it: (A) a 5 s Redis stall on every Bearer-authenticated
request, and (B) a deployment-wide 100 req/min rate-limit ceiling. Both are
config/app-level fixes; neither is a resource problem.

## 6b. Front Door edge — latency delta (per-request, low-volume)

The public edge `https://tst.numbatwallet.credentry.com.au` (Front Door → ingress)
came live during this exercise. Per-request timings (a few probes each — **no load run**,
see caveat below) compared with the direct-ingress path:

| path | direct ingress | Front Door edge | FD overhead |
|---|---|---|---|
| `GET /health` | ~0.115 s | ~0.24–0.29 s | **+0.12–0.18 s** |
| API-key `verifyPresentation` | ~0.118 s | ~0.234 s | **+0.12 s** |
| citizen login (`POST /Authentication/login`) | works | works (token issued) | — |

Front Door adds roughly **+120 ms per request** (edge TLS termination + FD→AU-ingress
backhaul). The fast app paths (health, credential reads, verify) remain under the
500 ms SLA through the edge (~180–260 ms), but the budget is tighter. The
Redis-bound citizen-journey path (~5 s) and the global rate-limit ceiling are
**unchanged** at the edge — Front Door forwards to the same ingress pod IP, so the
per-IP limiter still collapses to one shared bucket, and the Redis stall is unaffected.

> **Not executed:** a full 50-VU edge load run was requested by the coordinator but is
> **out of the user-authorized scope** (the user authorized documenting the edge re-run
> command, not running load against the shared Front Door). Only the low-volume probe
> timings above were taken. The harness is ready for the edge run — see `README.md`
> (§ Edge re-run); `PROFILE=edge` provides a bounded 50-VU / ≤2-min profile when authorized.

## 7. Caveats

- **No Front Door route yet** — tested against the ingress IP with a `Host` override; the
  public edge (Front Door → ingress) is not yet in the path. Re-run command in
  `README.md` (§ Edge re-run).
- **B1ms shared PostgreSQL** — adequate at the offered load here (queries 2–7 ms); not
  load-tested to its own ceiling because the rate limiter caps upstream throughput first.
- **`Testing` env overhead** — verbose EF Core + Serilog request logging adds latency
  vs a production logging profile.
- **No issuer-list API** (introspection disabled; `createOrganization`/`organizations`
  broken). The credential-ops **issue write-mix** and the **real presentation happy-path**
  were validated **locally** (seeded issuer GUID known). On AKS, credential-ops ran the
  read path and presentation-verify used a synthetic token (still exercises JWT
  parse + signature + jti DB lookup; HTTP 200, `isValid:false`).
- 429 responses are excluded from `http_req_failed` (marked expected) so the cluster
  abort guards fire only on real stress; the throttle share is reported as `throttled_429`.
